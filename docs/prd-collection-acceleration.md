# PRD：岗位采集提速与受控并行

| 项目 | 内容 |
| --- | --- |
| 状态 | 调研完成，待评审；本阶段不实施代码改动 |
| 日期 | 2026-08-30 |
| 负责人 | BossHunter 产品与工程 |
| 影响范围 | Web 采集任务、三平台采集器、采集运行记录、进度展示、自动评分 |

## 1. 结论

可以提升采集速度，但不应直接把现有采集循环改成多线程或将 BOSS 的页面并发打开。

推荐采用分阶段的混合方案：

1. 保持 BOSS 单浏览器工作标签、单平台串行，维持既有风控节奏和页面额度。
2. 先实现不增加浏览器访问频率的提速项：统一的列表级预筛、重复搜索组合跳过、采集和 AI 评分的流水线重叠。
3. 在观测数据和隔离能力到位后，试点智联与 51job 的平台级并行；BOSS 在试点阶段保持独占，不与其他平台同时采集。
4. 所有并行采集器各自使用数据库连接，由单独的写入者顺序落库，并由统一调度器负责停止、风险升级、进度和断点恢复。

默认模式仍为串行。加速模式必须由用户显式开启，且可一键自动降级为串行。

## 2. 背景与问题

当前多平台采集器已经可用，但总时长随平台、城市、关键词、页数和详情数线性累加。典型组合会经历：列表打开和加载、滚动、详情打开和加载、随机等待、保存、下一个平台。等待和网络 I/O 占比高，存在通过任务编排提速的空间。

现有系统并非没有并发能力：AI 评分已支持 1-3 个并发工作者，浏览器运行时也能按 `targetId` 操作多个标签页。但是岗位采集的持久化、风控、暂停恢复和 Web 任务状态均按单一串行队列设计，因此不能仅替换循环为线程池。

## 3. 现状调研

| 维度 | 观察 | 对并行设计的影响 |
| --- | --- | --- |
| 编排 | `CollectionOrchestrator.run` 逐个平台执行，类注释明确为严格串行队列 | 需要新调度层，不能在现有 `for` 循环中直接并发调用 collector |
| BOSS 浏览器工作流 | 一个后台标签在列表和详情间复用；每页与每个详情均有随机等待、二次风险确认和页面额度预留 | BOSS 内部并发会直接改变访问指纹和额度消耗节奏，第一阶段禁止 |
| BOSS 风控 | 验证码、拦截、限流、登录失效会锁定并停止整个队列 | 任何 BOSS 风险信号必须取消所有正在运行的浏览器采集工作 |
| 智联/51job 工作流 | 两者按城市、关键词、页和详情串行；会打开搜索及详情标签，并各自有等待或页面稳定性判断 | 可以作为“平台级并行”候选，但仍不能无上限并发标签 |
| 浏览器运行时 | HTTP 到 CDP 的桥接以 `targetId` 区分页面，会维护多目标 session | 技术上可支持多标签，但应增加目标数配额、标签归属和清理校验 |
| 数据库 | SQLite 使用 WAL，岗位有唯一来源身份索引；当前处理器共享一个连接，且每条岗位写入后提交 | 线程之间不得共用该连接；需要单写入者或专用写队列避免锁竞争与进度乱序 |
| 运行记录 | `collection_runs` 只有 `current_platform`，暂停后从当前平台重新开始 | 并行时必须记录多个活动平台和各自检查点 |
| 任务管理 | Workbench 同时只允许一个活跃任务 | 保留“一个采集任务”的产品语义；并行仅发生在该任务内部 |

### 3.1 关键源码依据

- 编排器在 [src/bosshunter/collection/orchestrator.py](../src/bosshunter/collection/orchestrator.py) 中按 `platform_order` 顺序调用采集器，并在任一阻断/停止信号后结束队列。
- BOSS 采集器在 [src/bosshunter/collection/platforms/boss.py](../src/bosshunter/collection/platforms/boss.py) 中复用 `worker_target`，并对搜索页、详情页、风险确认和等待实行顺序控制。
- 智联与 51job 采集器分别位于 [src/bosshunter/collection/platforms/zhilian.py](../src/bosshunter/collection/platforms/zhilian.py) 和 [src/bosshunter/collection/platforms/job51.py](../src/bosshunter/collection/platforms/job51.py)，均使用浏览器标签和页面级等待。
- SQLite 初始化启用 WAL，岗位以 `(source_platform, source_job_id)` 唯一索引去重，见 [src/bosshunter/db.py](../src/bosshunter/db.py)；这保证最终去重，但不适合多个线程共享同一连接。
- 当前任务和运行记录分别见 [src/bosshunter/web/tasks.py](../src/bosshunter/web/tasks.py) 与 [src/bosshunter/collection_run_store.py](../src/bosshunter/collection_run_store.py)。

## 4. 目标与非目标

### 4.1 目标

1. 在相同搜索配置和不提高 BOSS 页面访问额度的前提下，降低一次采集完成时间。
2. 不降低去重、关键词匹配、JD 过滤、风险检测、停止和暂停恢复的正确性。
3. 让用户可理解当前哪些平台在运行、哪些在等待、为何自动降级或停止。
4. 用真实运行指标决定是否开放更高并发，而不是仅凭理论吞吐上线。

### 4.2 非目标

- 不绕过验证码、频率限制、登录要求或平台访问规则。
- 不增加 BOSS 单日搜索页、详情页或总页面访问硬上限。
- 第一阶段不实施 BOSS 多标签/多详情并发，不多开 Chrome Profile，也不使用多个账号规避限流。
- 不允许多个用户发起的采集任务并行运行；仍只有一个 Workbench 活跃任务。
- 本 PRD 不包含代码实现、数据库迁移或界面视觉设计稿。

## 5. 方案决策

### 5.1 方案对比

| 方案 | 预期收益 | 风险/成本 | 决策 |
| --- | --- | --- | --- |
| BOSS 列表和详情多标签并发 | 理论上高 | 明显改变同账号访问节奏；现有风控、额度和单工作标签假设失效 | 不采用 |
| 三平台全部同时采集 | 中到高 | 共享 Chrome 会话、标签上限、SQLite 写冲突和全局停止语义均需重做 | 不作为首发 |
| 智联 + 51job 平台级受控并行 | 中 | 需要调度、写队列和目标配额；不触碰 BOSS 访问模式 | 第二阶段试点 |
| 采集与 AI 评分流水线重叠 | 中 | 需定义评分批次和数据库状态，浏览器风险不增加 | 第一阶段实施 |
| 列表级预筛与重复组合跳过 | 低到中 | 需保证不因缺少 JD 而误过滤 | 第一阶段实施 |
| 缩短随机等待/提高 BOSS 页数额度 | 看似直接 | 违反现有反监测设计，可能提升风控事件 | 不采用 |

### 5.2 推荐运行模式

| 模式 | 默认 | 平台调度 | 适用情形 |
| --- | --- | --- | --- |
| 安全串行 | 是 | BOSS、智联、51job 按用户顺序执行 | 所有新用户、风险冷却后、任何异常后 |
| 流水线加速 | 是 | 浏览器采集仍串行；已完整入库的一批岗位进入受限 AI 评分队列 | API 配额充足且开启自动评分 |
| 跨平台试点 | 否 | 仅智联和 51job 同时运行；BOSS 必须在两者结束后单独运行 | 连续稳定运行且用户显式开启 |

试点模式的全局浏览器工作者上限为 2。调度器还必须维护“浏览器目标令牌”：列表标签、详情标签各占一个令牌，达到总上限时工作者等待而非继续开标签。初始上限建议为 3 个目标，最终值以压测和真实稳定性数据确定。

## 6. 产品需求

### 6.1 配置与入口

1. 在采集设置中提供“采集速度”选项：`安全串行`、`流水线加速`、`跨平台试点`。
2. 默认 `安全串行`。跨平台试点首次开启时展示风险说明：该模式只对非 BOSS 平台并行，任一平台风控/浏览器异常会停止本轮并退回安全串行。
3. 后台保留一项仅用于受控发布的最大浏览器工作者配置，普通用户不可将其设为大于 2。
4. 自动评分关闭时，不启动评分流水线；评分并发仍遵守既有 `ai.scoring_concurrency` 上限。

### 6.2 调度规则

1. 一个 Workbench 采集任务拥有一个全局取消事件、一个调度器和一组平台工作者；外部仍只显示一个任务。
2. 安全串行遵循用户配置的 `platform_order`，结果与当前行为一致。
3. 流水线加速中，岗位只有完成详情解析、共享过滤和成功入库后，才能被放入 AI 评分批次；评分不得读取未提交的岗位。
4. 跨平台试点只允许智联和 51job 并行。BOSS 始终独占浏览器采集阶段，且不得与其他平台重叠。
5. 平台工作者不得共享 SQLite 连接、可变进度对象或浏览器标签。每个标签必须标记 `run_id`、平台和工作者，并在完成、失败、取消时关闭。
6. 所有岗位写入经单写入者串行执行。写入者按小批次提交，并用数据库唯一来源身份索引作为最终去重裁决。
7. 列表级去重可使用只读检查以避免无效详情访问；检查命中不影响最终唯一索引的正确性。
8. 调度器按平台维护令牌桶/最小间隔。现有 BOSS 随机等待、详情额度、搜索额度和风险冷却原样保留。

### 6.3 停止、风险与降级

1. 用户停止时，调度器禁止分配新列表/详情任务，向全部工作者发出取消，等待当前浏览器操作到达安全检查点，并保证已成功写入的岗位可见。
2. 用户暂停时，保存每个平台的状态和已入库 ID；恢复时只调度未完成的平台或未完成的组合。恢复过程允许再次看到已采集岗位，但必须由去重保证不重复入库。
3. BOSS 检测到验证码、限流、拦截或登录失效时，立即取消所有浏览器采集工作者，沿用已有风险事件和冷却逻辑。
4. 智联或 51job 检测到阻断、登录失效、页面结构变化或浏览器断连时，停止本轮跨平台试点，并将本次模式记录为“自动降级”；下次默认安全串行。
5. SQLite 写入连续失败、写队列积压超过阈值、浏览器目标清理失败或运行记录持久化失败时，停止分发新工作并以可诊断错误结束任务。

### 6.4 进度与运行记录

1. 进度 API 返回 `active_platforms` 数组，而不是仅依赖单个 `current_platform`；每项包含状态、当前城市/关键词/页、阶段、等待原因、已扫描/新增/重复/过滤/解析失败/保存失败。
2. 汇总进度须显示：当前模式、活跃工作者数、活跃浏览器目标数、写队列长度、评分队列长度、降级原因和风险状态。
3. 运行记录为每个平台保存独立检查点，至少包括未完成组合、页号、已处理来源 ID 的可选短期集合和最后安全边界。
4. 高频事件不得每次都立即写入 `collection_runs`。进度记录应合并为固定时间间隔或重要状态变更后持久化，避免状态写入本身成为瓶颈。

### 6.5 非浏览器提速项

1. 将当前 BOSS 的列表预筛能力抽象为所有平台可复用的、保守的候选筛选：来源 ID 已存在、标题命中否决词、公司黑名单、明确不满足基础条件时不再打开详情。
2. 关键词是否匹配 JD 仍以详情后的共享过滤为准；列表信息不足时必须保守放行，不能为提速误丢岗位。
3. 对同一运行中的 `(platform, city, keyword, page)` 建立完成记录，避免因重试、恢复或重复配置产生无意义重复访问。
4. 统计列表候选、详情打开、详情成功、预筛拦截和去重命中，用以判断下一轮优化应聚焦搜索质量还是浏览器等待。

## 7. 技术边界与数据契约

### 7.1 新的内部状态模型

采集运行记录需要从单值 `current_platform` 演进为下列逻辑结构。字段名可在技术设计阶段确定，但语义不可省略。

```json
{
  "mode": "safe_serial | pipelined | parallel_pilot",
  "active_platforms": ["zhilian", "51job"],
  "platforms": {
    "zhilian": {"status": "running", "checkpoint": {}, "metrics": {}},
    "51job": {"status": "waiting_browser_slot", "checkpoint": {}, "metrics": {}}
  },
  "writer": {"queue_depth": 0, "last_commit_at": ""},
  "scorer": {"status": "running", "queued": 0},
  "degradation": {"active": false, "reason": ""}
}
```

### 7.2 写入契约

1. 写入成功的唯一标准仍是岗位表中来源身份唯一索引插入成功。
2. 写入者失败后不得把候选标记为“已保存”；重试必须是幂等的。
3. 评分队列只接受写入成功返回的岗位 ID；重复岗位和保存失败岗位均不得进入本轮自动评分。
4. 任务结束前，调度器必须等待写队列清空或明确报告未写入数量，不得静默丢弃。

## 8. 分期与发布条件

| 阶段 | 内容 | 是否改变 BOSS 访问节奏 | 发布条件 |
| --- | --- | --- | --- |
| P0 基线 | 增加采集阶段耗时、详情成功率、风险事件、写入等待和评分等待的观测；采集逻辑保持串行 | 否 | 至少积累 30 次有效运行或足以覆盖三平台的受控样本 |
| P1 流水线 | 采集-写入-AI 评分重叠、保守列表预筛、重复组合跳过、写队列和新的进度模型 | 否 | 相同配置下中位总时长降低至少 20%，风险事件率与遗漏率不升高 |
| P2 并行试点 | 智联 + 51job 最多 2 个平台工作者、浏览器目标令牌、自动降级和每平台恢复 | 否，BOSS 独占 | 先灰度 10%，连续 7 天无 P1 级数据丢失/错误投递，失败和阻断可完整恢复 |
| P3 评估 | 根据试点数据决定是否扩大平台组合或长期保留试点 | 待定 | 吞吐收益显著且风控、稳定性、浏览器资源均通过阈值 |

P3 不预先承诺 BOSS 并行。是否重新评估只能基于单独账号风险评审、平台规则评估和专门实验，不能由 P2 成功自动推导。

## 9. 指标与验收标准

### 9.1 核心指标

| 指标 | 定义 | P1 目标 | P2 目标 |
| --- | --- | --- | --- |
| 采集总时长 | 从任务启动到全部平台采集结束，不含用户确认和投递冷却 | 同配置 P50 下降 >= 20% | 智联+51job 组合 P50 下降 >= 30% |
| 有效详情成本 | 成功入库岗位数 / 已打开详情页数 | 不低于基线 | 不低于 P1 |
| 保存可靠性 | `save_failed / attempted_save` | 不高于基线且 < 0.5% | 不高于 P1 且 < 0.5% |
| 运行稳定性 | 非用户主动停止的失败任务占比 | 不高于基线 | 不高于 P1 + 1 个百分点 |
| 风险事件率 | 每 100 次平台访问的风险/阻断事件 | 不高于基线 | 不高于基线 |
| 数据完整性 | 数据库唯一来源身份冲突、重复评分、遗漏写入 | 0 个 P1 事故 | 0 个 P1 事故 |

基线比较必须使用相同平台、城市、关键词、页数、网络环境区间和时间段的样本；未达到最小样本量时仅展示趋势，不宣称提速结论。

### 9.2 功能验收

1. 安全串行模式的测试结果与当前采集顺序、风控停止和数据库结果兼容。
2. 开启流水线后，采集未完成时可以开始评分已入库岗位；同一岗位最多进入一次本轮评分。
3. 跨平台试点中，智联和 51job 可同时展示独立进度，且活跃浏览器目标数永不超过配置上限。
4. BOSS 出现风险信号时，其他正在运行的平台在可取消检查点内停止，运行记录包含原始原因和被取消的平台。
5. 暂停/恢复、浏览器断连、写入失败和应用重启后，系统不会重复写入岗位，也不会将未写入岗位标为成功。
6. 自动降级后，新任务默认回到安全串行，并向用户说明原因。

## 10. 测试与观测要求

1. 单元测试：调度优先级、BOSS 独占、目标令牌、取消传播、单写入者幂等、评分批次去重和状态合并。
2. 集成测试：模拟两个平台交错产生岗位、SQLite 短暂锁、一个平台阻断、一个平台浏览器断连、暂停后恢复。
3. 回归测试：现有串行编排、BOSS 页面额度、风险冷却、Web 单任务互斥和 collection run 读取均不回退。
4. 端到端受控测试：每个平台使用最小页数和测试账号/人工监控；只记录必要的耗时和错误摘要，禁止采集或展示登录凭据。
5. 发布监控：按模式和平台切分仪表盘，至少包含阶段耗时、详情率、写队列深度、浏览器目标数、降级次数、风险事件和取消完成时延。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 平台限流或账号风险 | 采集受阻，可能影响账号 | BOSS 保持单通道；保持原有页面额度和等待；风险即全局取消并冷却 |
| 共享浏览器标签过多 | 页面错位、内存压力、标签泄漏 | 目标令牌、标签归属、finally 清理、结束时一致性检查 |
| SQLite 写锁或进度乱序 | 保存失败、任务状态不可信 | 每工作者独立连接、单写入者、批次提交、重试和幂等唯一索引 |
| 暂停恢复语义变化 | 重复访问或遗漏岗位 | 每平台检查点；数据库去重为最终裁决；恢复优先未完成组合 |
| AI API 竞争资源 | 评分限流、影响采集结束体验 | 沿用 1-3 并发上限，独立队列，超限时暂停评分而非浏览器采集 |
| 速度指标失真 | 为提速降低岗位质量 | 同时观察详情成功率、过滤质量、保存可靠性与风险率，不只看耗时 |

## 12. 待确认事项

1. P0 基线的采样窗口与最小样本量是否以 30 次有效任务为准，还是按平台分别设定。
2. 跨平台试点是否只对已登录且连续稳定完成过采集的用户开放。
3. 评分流水线是否允许在采集结束前向用户展示“已评分”岗位，还是仅在整个采集完成后统一刷新。
4. 是否需要在 P1 即引入历史搜索组合缓存；若需要，应确认缓存有效期和用户修改搜索条件后的失效规则。

## 13. 建议的下一步

评审通过后，先完成 P0 的基线观测设计和 P1 的技术设计评审，再开始代码实现。P2 必须以 P1 的真实数据和风险复盘作为进入条件，不能与 P1 同时上线。
